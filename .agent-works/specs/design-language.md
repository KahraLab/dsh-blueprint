# 设计语言

> Blueprint 里「设计语言」是什么、怎么存、怎么进来、怎么出去。照着做就行。

## 它解决什么问题

一个原型十几个屏幕，还可能换人来画。要让它们看起来像同一个人做的，画的人——不管是人还是 AI——得知道三件事：

1. 有哪些原料：颜色、字体、字号、间距、圆角、阴影、动效。
2. 原料怎么用：什么场合用主色，标题多大，留白多宽。
3. 用出来长什么样：一个卡片、一个表单、一个空状态，标准长相。

只给原料，画出来是「能用但没性格」；原料加规矩，好一点；三样都有，才稳。

## 一个文件，一处数字

设计语言就是一个 `DESIGN.md` 文件。里面只有两种东西：

- **正文**：用大白话写规矩、场合、反例、范例。
- **文末的令牌块**：一个 JSON 代码块，写死全部数字。

**数字只写在令牌块里。** 正文提到某个颜色、某个间距时，只写名字，比如「主按钮用 `color.primary`」，不写具体色值。

一个色值只写一遍。改的时候只有一处要动，不存在「上面改了下面没改」这种事。

这不是洁癖。业内实测过：规范里把 `danger` 写成了 `error`，一个词的偏差，AI 生成代码的编译通过率从 90% 掉到 70%。让模型去抄文字规范，本身就是碰运气。

## 文件长什么样

```
# 设计语言名字

## 概览           ← 气质、给谁用、一句话定位
## 颜色           ← 每个颜色是什么、用在哪
## 字体           ← 字体家族、字号阶梯
## 排版与间距     ← 容器宽度、间距节奏、密度
## 阴影           ← 哪个层级用哪一档
## 形状           ← 圆角规律
## 组件           ← 按钮、输入框、卡片的预设
## 动效           ← 时长、曲线、什么时候用
## 状态           ← 空、加载、错误怎么表现
## 该做与不该做   ← 最容易犯的错
## 范例           ← 能直接打开的 HTML 片段
## 令牌           ← 唯一的 JSON 数字块
```

章节顺序固定。可以不写的章节整节删掉，但写了的必须按这个顺序排。

## 令牌块

一个 JSON，分成几组：

```json
{
  "meta":    { "schema": 1, "version": 1, "name": "Harbor", "inferred": [] },
  "color":   { "primary": "#1F6FEB", "ink": "#101828" },
  "type":    { "body": { "fontFamily": "Inter", "fontSize": "14px", "fontWeight": 400, "lineHeight": 1.6 } },
  "space":   { "md": "16px" },
  "radius":  { "md": "10px" },
  "shadow":  { "sm": "0 1px 2px rgba(16,24,40,0.06)" },
  "motion":  { "fast": { "duration": "120ms", "easing": "cubic-bezier(0.2,0,0,1)" } },
  "component": {
    "button-primary": { "background": "{color.primary}", "color": "{color.on-primary}", "radius": "{radius.md}" }
  }
}
```

每组的意思：

| 组 | 存什么 | 值的样子 |
|---|---|---|
| `meta` | schema 版本、语言版本、名字、哪些值是猜的 | 数字和数组 |
| `color` | 颜色 | 任何合法的 CSS 颜色：`#1F6FEB`、`rgb()`、`oklch()` |
| `type` | 字体的完整组合 | 家族、字号、字重、行高、字距 |
| `space` | 间距阶梯 | 带单位：`16px`、`1rem` |
| `radius` | 圆角阶梯 | 带单位 |
| `shadow` | 阴影档位 | 完整的 `box-shadow` 值 |
| `motion` | 动效 | 时长 + 曲线 |
| `component` | 组件预设：底色、文字色、圆角、内边距、字体、边框 | 引用其他组，或直接给值 |

组名和 token 名能自定义，顺序不重要。引用别的 token 用大括号写全路径：`{color.primary}`。引用可以套引用，但不许绕成环。

## 正文怎么写

- 每节开头一句话说这节管什么。
- 只写规矩和场合，不写数值。要提数值就写 token 名。
- 写反例。只说「该这样」模型记不住，说「别这样」才记得住。
- 别写「要美观」「要现代」这种话。写能判断的：几级标题、最多几个主按钮、卡片之间留多宽。

## 状态怎么写

空、加载、错误这三种状态最容易各写各的，所以设计语言里要定死它们的骨架：

- 空状态：标题写事实（「还没有工单」），不写「抱歉」；必须带一句下一步做什么。
- 加载状态：用骨架屏，不用转圈；骨架形状要跟真实内容一致。
- 错误状态：说清楚发生了什么、能怎么办；不暴露技术细节。

具体长相放进「范例」，用代码写出来。

## 范例怎么写

「范例」一节里，每个范例是一段能单独打开的 HTML，上面一行小标题写清楚「这是什么、什么时候用」。

放代码不放截图：截图不能改、不能搬，AI 只能看着它猜；代码能直接拖进画布，能复制、能改、能拆。

范例只放**小块的标准长相**——一个卡片、一行表单、一个空状态。整屏是原型自己的事，塞进语言里会跟原型不同步。

## 从别处导入

按可靠性排队，前面的赢后面的：

| 顺序 | 来源 | 怎么处理 |
|---|---|---|
| 1 | 现成的 `DESIGN.md`（我们的格式） | 直接读，无损 |
| 2 | DTCG 格式的 `tokens.json`（W3C 设计 token 标准） | 按类型映射 |
| 3 | Tailwind 配置（v3 的 `theme.extend` 或 v4 的 `@theme`） | 取颜色、字号、间距、圆角 |
| 4 | 普通 CSS 的 `:root` 变量 | 取能对上名字的 |
| 5 | 截图、设计稿 | 推断，每个值标「猜的」 |
| 6 | 一句文字描述 | 模型起草，整份标「猜的」 |

同一层里冲突时，先看名字对不对得上（`primary`、`secondary`、`neutral`），对不上的进待确认，不自己挑。

**猜出来的值必须标出来**：在 `meta.inferred` 里列路径，比如 `["color.tertiary", "space.xl"]`。值本身还留在原位，不重复写。界面上这些值显示成「待确认」，你点头之后从列表里删掉。

缺东西明说，不偷偷补：只导进颜色、没导进字体，就写「字体没找到，先用系统默认」。

## 导出

真相永远是这个 `DESIGN.md`。其他格式都是从它生成的产物，不往回改：

- **原样复制**——放进真实代码库，任何 AI 编码工具都能读。
- **标准 DESIGN.md**——把令牌块转成 YAML 放在文件头，给外部工具用。
- **DTCG JSON**——给已经有 token 流水线的工程。
- **Tailwind v3 配置 / v4 的 `@theme` CSS**——给用 Tailwind 的工程。

这几条都得我们自己写，不能用现成 CLI：实测官方导出会丢掉整个组件段、把别名拍平、把阴影和动效直接扔掉。发出丢的东西，等于交了个残废的规范。

交出原型时，交付包里放原文，不放摘要。

## 版本与引用

```
.dsh-blueprint/
  design-languages/
    harbor/
      DESIGN.md
      history/1.md
  prototypes/
    checkout/blueprint.json    ← 记着：harbor，版本 1
```

- 一套语言一个文件，原型只记「用了哪套、哪个版本」，不复制内容。
- 改一次，版本号加一，上一版自动进 `history/`。
- 有原型还在用旧版本时，提示「有 3 个原型受影响」，升不升由你决定，不悄悄改掉已做好的东西。
- 想试另一种风格，复制一套改名字，别在原套上动。

## 渲染器怎么读

- 只读文末那个 JSON 块。正文和范例不进渲染，只喂给 AI 当上下文。
- 令牌拍平成路径表，转成 CSS 变量，挂在 `[data-bp-dl]` 这个作用域上——**永不设在 `:root`**，否则会漏进 DSH 自己的界面和其它插件。
- 变量名规则：路径 `color.primary` → `--bp-color-primary`；复合值展开成 `--bp-type-title-font-size`、`--bp-type-title-font-weight` 这种扁平变量。
- 图层样式只允许引用变量，不许写字面值。
- 导出 HTML 时内联同一份 CSS 字节，用内容 hash 断言「编辑器看到的 = 导出的」。

## 校验

保存前跑一遍，错了不让存：

- 引用了不存在的 token。
- 两个 token 互相引用，绕成环。
- 组件前景色和背景色对比度不够（正文 4.5:1，大字和非文字元素 3:1）。
- 定义了却从没被用过的颜色。
- 缺主色、缺字体定义。
- 图层里出现写死的值，而不是引用 token。

结构检查可以借现成工具，但对比度、非文字对比、字面值、拍平冲突这几条必须自己写——现成工具只查一部分，而且章节顺序检查在中文标题下会静默失效，等于没查。
