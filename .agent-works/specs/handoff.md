# 交接协议

> 原型定稿以后，交给写代码的 AI 时交什么、怎么交、怎么判断做得对不对。

## 一句话

交接包是一个自包含的目录：设计语言、原型文档、每屏的参考实现、一份 Markdown 实现说明，外加一份能勾的验收清单。

## 包里有什么

```
handoff/<原型 id>/
├── README.md          入口：这是什么、从哪读起、怎么跑
├── DESIGN.md          设计语言原文
├── <原型 id>.blueprint.json   原型文档原文
├── screens/
│   ├── tickets.html           参考实现，单文件、能单独打开
│   └── ticket-detail.html
└── IMPLEMENT.md       逐屏实现说明 + 验收清单
```

| 文件 | 给谁看 | 作用 |
|---|---|---|
| `README.md` | 人，也顺带给 AI | 三分钟看懂这是什么、按什么顺序读 |
| `DESIGN.md` | 人、AI、构建工具 | 颜色、字体、间距、组件的唯一来源 |
| `<原型 id>.blueprint.json` | 工具链、AI | 屏幕、状态、跳转、动作节点的结构化真身 |
| `screens/*.html` | AI、人 | 能打开的参考实现，用来看效果、量尺寸、对结构 |
| `IMPLEMENT.md` | AI 主要读，人负责核对 | 逐屏怎么实现、哪里不能改、做完怎么验收 |

设计语言和原型文档都是**复制进包**，不是引用外部路径。包拷走就能用，换机器也不会散。

## README.md 写什么

1. 这个原型是什么产品，给谁用，解决什么问题。
2. 阅读顺序：先看 `screens/` 里任意一个，再读 `IMPLEMENT.md`，需要查数值时翻 `DESIGN.md`。
3. 怎么打开参考实现：双击即可，不需要装依赖。
4. 一句必须写的话：`screens/` 是参考实现，不是生产代码，不要整段复制进项目。

## IMPLEMENT.md 写什么

按这个顺序：

1. **产品是什么**：一两段，讲清楚这东西给谁解决什么问题。
2. **主流程**：几条主线，每条一句话带过经过哪些屏幕。
3. **逐屏说明**：每屏一节，固定字段。
4. **跨屏规则**：统一的错误处理、加载表现、跳转约定。
5. **非界面步骤**：发邮件、等审核、支付回调这些动作节点怎么实现。
6. **验收清单**：能勾的条目。
7. **开工前的复述要求**。

单屏的固定字段：

```markdown
## 工单列表 · tickets

看和处理工单。

**状态**
- 默认：有数据
- 空：一条都没有，显示空状态，带「新建工单」
- 加载：骨架屏，形状跟列表一致
- 错误：加载失败，显示重试

**从哪来、去哪**
- 点卡片 → ticket-detail
- 点「新建」→ ticket-new
- 未登录 → sign-in

**数据**
- 列表来自 GET /api/tickets，字段 id / title / status / assignee / updatedAt
- 原型里是假数据，实现时替换

**别改**
- 一屏只能有一个主按钮
- 空状态文案保持原样
```

**设计意图怎么写**：能说清楚就写，说不清楚就写「未提供」。不编。编出来的理由比没有理由更害人——AI 会拿它当依据改设计。

## 验收清单

每条都要能判断「过了」还是「没过」，不写「风格统一」这种没法验的话。

```markdown
- [ ] 每个屏幕都存在，id 与 `<原型 id>.blueprint.json` 一致
- [ ] 每个屏幕的空 / 加载 / 错误状态都能实际触发
- [ ] 所有跳转按条件生效，走不回去的死路数为 0
- [ ] 关键文案与原型逐字一致（见上方各屏「别改」）
- [ ] 颜色、字号、间距、圆角只来自 DESIGN.md 的 token，没有写死的色值
- [ ] 没有把 screens/*.html 整段复制进生产代码
- [ ] 动作节点（发邮件、支付回调）在代码里有对应实现，不是占位注释
```

## 开工前的复述

在 `IMPLEMENT.md` 末尾写死这段要求，让 AI 读完先复述再动手：

> 开始写代码之前，先用三句话复述：这个产品是什么、有哪几条主流程、你打算先做哪一块。复述与本文档对不上时先提问，不要猜。

复述是提前暴露理解偏差最便宜的办法。等代码写完才发现方向错了，代价大得多。

## 参考实现的边界

- 每个屏幕一个**单文件 HTML**，CSS 内联，双击就能打开。
- 文件里用的颜色和尺寸来自设计语言，但**值已经展开**，不依赖外部文件。这样包是自包含的。
- 参考实现里可以有假数据、假状态切换，用来演示交互。
- 不允许出现真实接口调用、密钥、构建配置。
- 文件顶部写一行注释：`<!-- 参考实现，不是生产代码 -->`。

插件运行时禁止把变量挂到 `:root`，那是为了不污染宿主界面；参考实现是独立文档，没有这个问题，可以在文件内用 `:root`。

## 什么时候生成

- 工作台里点「交接」，或在对话里说一句「生成交接包」。
- 输出到工作区根的 `handoff/<原型 id>/`。一个原型一个子目录，多个原型不会互相覆盖。
- 每次整包重新生成：先写到临时目录，写完整了再整体替换，避免生成到一半留下半个包。
- 不要求原型已经「定稿」。随时可以生成，改完再生成一遍即可。

## 和 DSH 现有机制的关系

- 编码 Agent 就在同一个工作区里干活，它有文件读写工具，能直接读 `handoff/`。不需要额外的传输机制。
- `present` 只用来把最终的包或截图交到用户手上，不参与交接内容本身。

## 不做什么

- 不生成生产代码。原型里怎么写的不重要，写代码的 AI 按自己项目的规范来。
- 不猜接口。数据来源不清楚就写「未提供」，留给实现时确认。
- 不替用户选技术栈。交接包与框架无关。
