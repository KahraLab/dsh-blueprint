## Question

把 Blueprint 的领域模型定死，并写进 `GLOSSARY.md`：Blueprint（文件）、屏幕、转移、状态、图层、设计 token、交付包。

要逐个回答的边界问题：

- **(a)** 屏幕与画板是不是同一个东西？一个 Blueprint 里多屏幕怎么组织（平铺？分组？）
- **(b)** 一个屏幕的多状态（空/加载/错误/无权限）是兄弟画板、还是屏幕的 `state` 字段、还是独立的 Overlay？
- **(c)** 转移挂在什么上：热区（元素级）、屏幕（屏幕级）、还是显式的转移对象（元素 → 屏幕 + 条件）？
- **(d)** 流程里的「非界面步骤」（发邮件、支付回调、后台任务）怎么表达？纯界面原型会漏掉真实流程的关键段。
- **(e)** 组件（component）和实例（instance）进不进 v1？如果进，引用/覆盖/解绑三层语义怎么定。
- **(f)** 设计语言与 Blueprint 是什么关系？独立存放被引用（一对多）、每个 Blueprint 内嵌一份、还是全局唯一一套。它算不算第四种一等对象。

产出：更新后的 `GLOSSARY.md` + 一张领域模型图（文本或 mermaid）。

## Resolution

2026-10-28 定稿。

- **(a) 屏幕 = 画板**：不引入独立画板概念。一个屏幕就是一块画布 + 流程元数据（名称、状态、转移）。
- **(b) 状态 = 基础树 + 差异**：屏幕有 states，每个状态只存相对基础元素树的差异（空 / 加载 / 错误），不复制整棵树。
- **(c) 转移 = 显式对象**：源屏幕 + 触发（元素 id 或事件）+ 目标节点 + 条件。
- **(d) 非界面步骤 = 动作节点**：流程节点分「屏幕节点」与「动作节点」。动作节点没有画布，在总览里显示为卡片，可连接前后转移（发邮件、等审核、支付回调）。
- **(e) 组件 = 薄实例进 v1**：主组件 + 实例 + 局部覆盖；解绑、嵌套实例、变体矩阵后置到 v1.1。
- **(f) 设计语言 = 独立对象、原型按版本引用**：存于 `design-languages/<name>/`；Blueprint 记录引用版本；语言升级是显式操作并提示受影响原型；可复制一份做风格试验。

**对下游的影响**：patch 协议（AI 编辑协议）必须能覆盖状态差异、实例覆盖、转移与动作节点；存储（插件架构与存储）要处理语言版本与引用。
